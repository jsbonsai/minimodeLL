## Findings (each observed, not inferred)

1. Sandbox denies `bind()` without `com.apple.security.network.server` (`deny(1) network-bind local:*:0`). The inheriting child needs the same right to listen, so the app entitlement is required.
2. Hardened runtime + ad-hoc signatures: dyld refuses the bundled dylibs ("different Team IDs"). Ad-hoc builds sign `llama-server` without hardened runtime. With a Developer ID all code shares a Team ID, so hardened runtime should work — **unverified**.
3. App Sandbox denies `proc_pidfdinfo` on children (`process-info-pidfdinfo`), so a libproc "who owns this port" check is impossible in the packaged app. Replaced by a key challenge (401 without key, 401 with random decoy key, 200 with real key + expected alias + `n_ctx`).
4. `llama-server` `/health` is unauthenticated; `/v1/models` and `/v1/chat/completions` require the key (verified with curl).
5. Without a supervisor, SIGTERM/SIGKILL of the app orphaned `llama-server` (ppid 1). The guard fixes both (verified).
6. The sandboxed helper cannot read a model outside the container even through a symlink inside `Models` (`deny(1) file-read-data`).
7. First-ever launch took ~23 s to readiness (probably one-time Metal shader/cache work); later launches were ~0.3–0.5 s for the 135M model.
8. Running `osascript -e 'quit app "minimodeLL"'` at the start quit a minimodeLL instance that was running from the main checkout (`/Users/apple/dev/minimodel/build/…`, pid 20579). If another agent was using it, it needs relaunching.

## Decisions

Recorded in ADR 0008: helper not in-process; pinned official prebuilt (source build later); env-var key not argv; key challenge not libproc; guard supervisor; lazy start; leases gate idle unload; no automatic restart; no cloud fallback; `modelFile` is a name in the container `Models` folder, never a path.
