Why this exists

Local AI that an IT team can actually say yes to.

Consumer local-model apps let anyone install anything and point it anywhere. Cloud assistants move company context off the machine. {{NAME}} sits in between: small, native, and governable.

01

Policy is enforced in code, not in a prompt.

Which models, which servers, which tools, and which of those need a human first are all decided by a typed, validated policy the app cannot talk its way around. A system prompt or MCP annotation is never an authorization boundary.

02

One task, one bounded run.

Each task starts with a fresh context, one tool call per model response, and hard limits on input, context, output, steps, result size, and wall time. Nothing runs in the background and writes are never retried automatically.

03

Useful alone. Governable at fleet scale.

An individual can configure the app themselves. An organization can ship a complete, forced policy through Jamf or Iru (formerly Kandji) that the user cannot extend. Same app, same schema, same validator.

Governance

How policy flows from the MDM to the task.

Policy is resolved again for every submission and captured as one immutable snapshot for the run. Managed policy replaces user configuration entirely; if it is invalid, the app fails closed and blocks requests rather than falling back.

1

IT publishes a forced policy

A configuration profile delivers PolicyJSON into the org.minimodell.agent managed preference domain. The repo generates the profile from the same JSON the app validates, so what IT scopes is what the app enforces.

2

The app resolves one effective policy

Forced managed policy → user config.json → bundled defaults. First match wins, completely. User settings can never add a model, server, or tool to a managed allowlist.

3

Every step is checked and recorded

Tool calls are validated against a JSON Schema subset and the allowlist, then held for human approval when the policy says so. Each step writes a metadata-only audit event; if the audit write fails, the task halts.

Approval is about arguments. The confirmation sheet shows the actual tool arguments, not the model's explanation of them. Set requiresConfirmation: false only for operations you have reviewed as safe.

Audit is content-free by design. JSONL and OSLog carry timestamps, run IDs, event categories, and model, server, and tool IDs. Prompts, responses, tool arguments, results, and tokens are never logged.

Cloud only when chosen. A LiteLLM gateway is an explicit HTTPS provider the policy must list and the UI labels before submission. The app never switches from local to cloud on its own.

What is in the preview

The pieces, and where they stand.

Everything below exists in code today. Where a piece is unit tested, fixture tested, or still waiting on live validation is spelled out in the project state.

Approved model catalog

Model stubs name a provider alias plus minimum memory and context length. Local providers must be literal loopback HTTP; remote ones must be HTTPS. Redirects are refused.

Allowlisted MCP tools

Exact tool names per server, discovered over Streamable HTTP with the official Swift SDK. Unknown tools, invalid arguments, and unsupported schema keywords are rejected, not ignored.

Human approval

Per-tool requiresConfirmation is owned by the app's policy. Server annotations do not grant approval. One tool call per model response keeps every decision reviewable.

Bounded execution

Input bytes, a conservative context estimate, output tokens, tool steps, result bytes, and wall time are all capped. A task that will not fit is refused before inference starts.

Content-free audit

Bounded JSONL files plus OSLog events with metadata only. Files are private to the user; central collection is a deployment concern, and nothing is uploaded automatically.

No silent cloud fallback

LiteLLM is a first-class, explicit choice for approved cloud models. It is labeled in the UI, listed in policy, and never used as a backstop when the local server is down.

Keychain-only credentials

Gateway tokens and MCP OAuth tokens live in the Keychain, bound to endpoint and client ID. Native browser sign-in uses PKCE; there are no bundled client secrets.

Sandboxed native app

SwiftUI, App Sandbox, Hardened Runtime, and a separate read-only diagnostics CLI so an MDM script can validate policy without launching the user's UI.

Architecture

Three Swift targets. One place where policy lives.

LocalAgentCore owns policy, orchestration, providers, credentials, and audit. MinimodeLL is presentation only. AgentDiagnostics validates configuration offline. Jamf and Iru integration is scripts and documentation; there is no MDM API dependency.

The inference runtime is an external process in this preview. Bundling a pinned, signed llama.cpp helper with app-controlled authentication and lifecycle is the next milestone. Read the full architecture notes and the decision records.

Status

Honest about where it is.

This is a developer preview. It builds, its safety boundaries are unit tested with deterministic fakes, and the packaged app is sandboxed. Live model quality, enterprise OAuth interoperability, notarization, and enrolled-device MDM behavior are still ahead of it.

Works today

  • Native app: task window, menu bar, settings, cancellation, and explicit tool approvals.
  • Providers: OpenAI-compatible loopback inference and explicit LiteLLM gateway configuration.
  • MCP: official Swift SDK, Streamable HTTP, tool discovery, native browser OAuth with PKCE, Keychain tokens.
  • Policy: versioned schema, forced MDM override, fail-closed validation, profile generator, diagnostics CLI.
  • Safeguards: all execution budgets, schema subset checks, approvals, and content-free audit, covered by deterministic tests in CI.
  • Packaging: sandboxed, ad-hoc signed .app, plus DMG and PKG build scripts.

  • Production release: Developer ID signing, notarization, accessibility polish, exact token accounting. Roadmap

Getting started

Build it in three commands.

You need an Apple Silicon Mac, macOS 14 or newer, Xcode 16.4 / Swift 6.1 or newer, and Git. The app needs no Python or Node runtime; packaging and profile scripts use the Python that ships with Xcode's command line tools.

01Test, package, open

Runs the deterministic core tests, builds a sandboxed, ad-hoc signed .app, and launches it. swift run minimodell is fine for UI work but does not exercise the sandbox.

swift test
scripts/package-app.sh
open build/minimodeLL.app

02Preview the UI without a model

A labeled fixture answers on the local port with a canned response and makes no outbound requests. Stop it before starting a real server on the same port.

python3 scripts/mock-inference.py

03Connect a local model

The preview talks to an existing llama-server; it does not bundle or download a runtime or weights yet. The starter configuration expects the alias local-model.

llama-server --model /path/to/approved.gguf --alias local-model \
  --host 127.0.0.1 --port 9931 --ctx-size 8192 --parallel 1 --jinja

04Validate and ship a policy

The diagnostics CLI validates a policy offline and exits nonzero on failure. The profile generator turns the same JSON into a configuration profile for Jamf or Iru.

swift run minimodell-diagnostics --config Config/enterprise.example.json
scripts/make-profile.py Config/enterprise.example.json build/minimodell.mobileconfig
